# SAP CAP (Cloud Application Programming) Reference Architecture & Quality Standard
> **Target Audience:** Developers, Technical Leads, and AI Agents auditing, designing, or implementing Node.js-based SAP CAP services.
> **Benchmark Source:** `intl-customer-master-data-cap`
> **Purpose:** Prevent AI hallucinations, enforce strict architectural discipline, establish security/governance baselines, and guarantee maintainable, production-ready CAP applications.

---

## 2. Directory & Component Architecture Blueprint

Every compliant CAP project must organize responsibilities into clean, non-overlapping domains:

```text
<project-root>/
├── app/
│   └── router/                          # Standalone Approuter (optional if using Managed Approuter)
├── db/
│   ├── schema.cds                       # Core domain entities, aspects, compositions, relationships
│   ├── data/                            # Initial seed data (.csv) named <namespace>.<Entity>.csv
│   └── undeploy.json                    # HANA artifact undeployment manifest
├── srv/
│   ├── cat-service.cds                  # Service definition: projections, actions, functions, annotations
│   ├── cat-service.js                   # Service entry point: lifecycle hooks registration & delegation
│   ├── auth.js                          # Hybrid authorization middleware & row-level security filters
│   ├── handler.js                       # Primary business workflows (state machine, numbering, audit history)
│   ├── masterData-handlers.js           # Reusable upsert operations for master data and localized texts
│   ├── helpers.js                       # Domain helpers (role lookups, approver maps, comment generators)
│   └── lib/
│       └── blob-storage.js              # Azure Blob Storage client wrapper (singleton instance)
├── test/
│   ├── *.http                           # REST Client test files (authenticated and mock requests)
│   └── *.js                             # Jest or Mocha integration test suites
├── scripts/                             # Maintenance & seed scripts (e.g. load-csv-data.js)
├── server.js                            # Custom server bootstrap (mounts OData V2 adapter, custom middleware)
├── eslint.config.mjs                    # ESLint configuration ([...cds.recommended])
├── xs-security.json                     # XSUAA security configuration (scopes, role templates)
├── mta.yaml                             # Multi-Target Application manifest for SAP BTP Cloud Foundry
└── package.json                         # Dependencies, scripts, and cds.requires configuration
```

## 3. Data Modeling Standards (`db/schema.cds`)

### 3.1. Entity Design & Inheritance
1. **Always use standard CDS aspects:** Inherit from `managed` (`createdAt`, `createdBy`, `modifiedAt`, `modifiedBy`) from `@sap/cds/common` for audit traceability.
2. **Explicit Keys and Types:**
   - Use meaningful business keys (e.g. `key code : String(10)`) for master catalogs.
   - Use UUIDs (`key ID : UUID;`) for transactional/header entities.
   - Constrain string lengths strictly (`String(4)`, `String(100)`). Never leave unbounded `String` in persisted database tables.
3. **Localization:**
   - Mark translatable attributes as `localized String(...)` (e.g. `name : localized String(100);`).
   - Let CAP manage `.texts` tables automatically unless custom upsert actions explicitly require manual maintenance.
4. **Relational Integrity:**
   - Use `Association to one` for independent foreign keys (e.g. Country, Currency, Office).
   - Use `Composition of many` for parent-child lifecycles (e.g. `offices : Composition of many SalesOfficeOrganization on offices.salesOrganization = $self;`).
   - Use dedicated junction entities for Many-to-Many ($N:M$) mappings with composite primary keys.

## 4. Service Modeling Standards (`srv/cat-service.cds`)

### 4.1. Projections & Views
- Never expose raw DB entities directly; expose projections:
  ```cds
  entity SalesOrganizations as projection on agrosuper.SalesOrganization;
  ```
- Use denormalized projections (`CustomerRequestsList`) for heavy UI list consumption, flattening deep relations into direct scalar fields for high read performance.
- Declare runtime fields as `virtual`:
  ```cds
  virtual null as canApprove : Boolean @title: 'Can Approve';
  virtual null as canReject  : Boolean @title: 'Can Reject';
  ```

### 4.2. Actions vs. Functions
- **`function`**: Use for read-only operations that do not modify state (e.g. `getUserInfo()`, `listDocuments()`).
- **`action`**: Use for side-effect operations, workflow transitions, and mutations (e.g. `submitForApproval`, `approveRequest`, `upsertSalesOrganization`).
- Return structured status contracts:
  ```cds
  action approveRequest(ID: UUID) returns {
      success : Boolean;
      status  : String;
  };
  ```

## 5. Implementation & Handler Guidelines (`srv/*.js`)

### 5.1. Delegation Pattern (Zero-Bloat Service Entry)
The main service file (`cat-service.js`) must strictly act as a **traffic controller**. It registers events and delegates immediately to modular handlers:

```javascript
// GOOD: Clean delegation
const handler = require('./handler');
const masterDataHandler = require('./masterData-handlers');
const { authorize } = require('./auth');

module.exports = cds.service.impl(async function () {
    this.before('READ', 'CustomerRequestsList', authorize(['SM', 'CONTROLLER', 'GVI']));
    this.on('getUserInfo', req => handler.getUser(req));
    this.on('submitForApproval', req => handler.submitForApproval(req));
    this.on('upsertSalesOrganization', req => masterDataHandler.upsertSalesOrganization(req));
});
```

### 5.2. Hybrid Authorization Architecture
CAP projects must implement a two-tier security model:
1. **Tier 1 (BTP Identity):** BTP verifies the OAuth token with scope `$XSAPPNAME.Access`.
2. **Tier 2 (Database-Driven Business Roles):**
   - Query user profile and business roles from the local `User` and `UserRole` tables using the verified email `req.user.id`.
   - Compute fine-grained workflow permissions (`canApprove`, `canReject`, `canCreate`).
3. **Row-Level Security (RLS):**
   - Intercept queries on sensitive views and inject dynamic SQL `WHERE` conditions based on user assignments:
   ```javascript
   req.query.where({ salesOffice_code: { in: assignedOffices }, createdBy: req.user.id });
   ```

### 5.3. Workflow State Machine & Audit History
1. **Linear Transitions:** Enforce allowed status paths (`DRAFT` -> `PENDING_CONTROLLER` -> `PENDING_COUNTRY` -> `PENDING_GVI` -> `APPROVED`).
2. **Immutable Audit Trail:** Every status mutation must insert a record into `RequestHistory` capturing:
   - `request_ID`, `fromStatus_code`, `toStatus_code`, `actorUser`, `actorName`, `actorRole`, `comments`, and timestamp.
3. **Atomic Numbering:** Avoid client-supplied document numbers. Generate deterministic, sequential numbers (e.g. `REQ-YYYY-NNNNN`) server-side within the creation hook.

## 6. Critical Audit Checklist for AI & Reviewers

When reviewing or generating CAP code, verify compliance against these critical checkpoints:

### 🔴 Critical Security & Integrity Rules
- [ ] **No Commented-Out Authorization:** Every mutation action and sensitive READ must have an active authorization guard. Never deploy with commented-out `this.before(..., authorize(...))` lines.
- [ ] **No Anonymous Fallback in Production:** Never default `req.user.id` to `'anonymous'` or `'system'` without throwing an HTTP 401/403 when running with auth enabled.
- [ ] **SQL/CQL Injection Prevention:** Always use parameterized CQL queries (`.where({ code: sCode })`) or tagged templates. Never concatenate strings into queries.
- [ ] **Concurrency-Safe Key Generation:** Concurrency locks or DB sequences must be considered for high-volume document numbering to prevent collision.

### 🟡 Architecture & Code Quality Rules
- [ ] **OData V2 Compatibility:** If UI5 consumes OData V2, `server.js` must mount `@cap-js-community/odata-v2-adapter` during the `cds.on('bootstrap')` phase.
- [ ] **No Dead Code in Source Control:** Build artifacts in `gen/` and `.mtar` archives must be excluded from Git via `.gitignore`.
- [ ] **Separation of Concerns:** Business logic must not reside inside CDS files or directly inline in `cat-service.js`. Separate into `auth.js`, `handler.js`, and `helpers.js`.
- [ ] **Error Contract:** Always return standard CAP error rejections (`return req.error(400, 'message')` or `req.reject(...)`), not unhandled generic JS exceptions.

## 7. Anti-AI-Hallucination Guidelines for Developers

AI assistants frequently introduce subtle bugs into SAP CAP codebases. Developers and prompts must adhere to the following anti-hallucination guardrails:

| Hallucination / AI Anti-Pattern | Correct CAP Pattern |
| :--- | :--- |
| **Inventing Express `next()` in CAP handlers:** `async (req, res, next) => { next(); }` | CAP event handlers take `(req)` or `(req, next)` where `next()` executes the default generic CAP handler. |
| **Using `new Date()` directly for CDS timestamps:** | Use ISO-8601 strings: `new Date().toISOString()` or let `@cds.on.insert: $now` manage it. |
| **Mixing up CQL with SQL:** e.g. `SELECT * FROM table` | Use CDS QL: `SELECT.from(Entity).where({ ... })` or `SELECT.one.from(...)`. |
| **Using `res.json()` or `res.send()` in CAP:** | In CAP service handlers, return the payload directly: `return { success: true };` |
| **Bypassing CDS validation:** | Do not mutate raw database tables directly when business logic or validations exist on projections. |
| **Hardcoding DB schema names:** e.g. `INTL_CUSTOMER_MASTER_DATA_CAP.ENTITY` | Use CDS entity references: `cds.entities('<namespace>')` to keep code DB-agnostic. |
